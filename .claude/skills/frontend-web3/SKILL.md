# Frontend web3

## Always use this project's hooks, not raw Wagmi

`packages/nextjs/hooks/scaffold-eth` wraps Wagmi/Viem with this project's
conventions (correct chain, correct ABI from `deployedContracts.ts`, typed
args). Use these, not `useReadContract`/`useWriteContract` directly, unless
you have a specific reason Wagmi's raw hooks don't cover:

- `useScaffoldReadContract` — reads (not `useScaffoldContractRead`, an old
  name that no longer exists)
- `useScaffoldWriteContract` — writes (not `useScaffoldContractWrite`)
- `useScaffoldEventHistory` — historical + live event logs
- `useScaffoldWatchContractEvent` — live-only event subscription
- `useDeployedContractInfo` — address/ABI for a contract by name
- `useScaffoldContract` — a viem contract instance
- `useTransactor` — wraps a write with toast notifications for pending/
  success/error states (use this instead of hand-rolling transaction UX)

## Every transaction must communicate

Per this project's UX bar (see `AGENTS.md`): what the user is doing, which
network, whether wallet approval is needed, and pending/success/failure state
with an explorer link. `useTransactor` + `notification` from
`~~/utils/scaffold-eth` cover this — use them rather than a bare
`writeContractAsync` with no feedback.

Handle explicitly, don't leave the user staring at a disabled button:

- Wallet not connected → prompt to connect (RainbowKit's
  `RainbowKitCustomConnectButton` in `components/scaffold-eth/`)
- Wrong network → `useTargetNetwork` + RainbowKit's network switcher
- User rejected the transaction in their wallet
- Insufficient funds
- RPC error / stale read (show a retry, don't fail silently)
- Reverted transaction → surface the revert reason via `getParsedError`

## UI components

Use `@scaffold-ui/components` for address/balance/input widgets (`Address`,
`AddressInput`, `Balance`, `EtherInput`, `IntegerInput`) rather than building
these from scratch — they already handle ENS resolution, blockie avatars,
explorer links, and wei/ether conversion. Use DaisyUI classes
(`btn btn-primary`, `card bg-base-100`) over raw Tailwind when a DaisyUI
component exists — see `AGENTS.md`'s Code Style Guide for the exact
convention.

## Network configuration

`packages/nextjs/scaffold.config.ts`'s `targetNetworks` array is the single
source of truth — the network selector, burner-wallet visibility
(`burnerWalletMode`), and RPC resolution all derive from it. Add a chain there
(and a matching `[rpc_endpoints]` entry in `packages/foundry/foundry.toml` if
contracts will be deployed to it), never hardcode a chain elsewhere.

## Contract data source

`packages/nextjs/contracts/deployedContracts.ts` is auto-generated by
`yarn deploy` — never hand-edit it (a comment at the top says so; believe it).
For a contract that isn't deployed by this repo (an external token, an
existing protocol contract), add it to `externalContracts.ts` instead.
